# alibre-script-runner — Code Review (Correctness)

**Date:** 2026-06-20
**Scope:** Second-opinion review, code only (correctness bugs). The project is pure IronPython (no .cs/.vb/.csproj/.adc). Reviewable runner code: `source/main.py`, `source/main_ex1.py`, `source/main_ex2.py`, `source/main_ex3.py`, `source/prototypes/Equation-Editor-Function-Calling.py`, `source/scripts/ex_as_fun_1.py` (raw example listings), `source/scripts/ex_as_fun_2.py` (function-wrapped examples). `source/randd/spline-tools.py` is empty (0 bytes). The example bodies are real, runnable code (run via `exec`/menu callbacks), so they are in scope.

**Summary: 11 bugs — 4 High, 4 Medium, 3 Low**

## High
- **`source/main_ex2.py:46,48,50`** — `run_example` calls `Win.InfoDialog(...)` / `Win.ErrorDialog(...)`, but `Win` is never defined anywhere in this file (no `Win = Windows()` and no `Windows` import). Every menu click raises `NameError`, so the runner cannot report success or failure for any script — the error path itself throws.
- **`source/main_ex2.py:46,48,50`** — f-strings (`f"Executed: {script_name}"`, etc.) are used. The Alibre Script engine is IronPython 2.7 (per README), which does not support f-strings; this is a `SyntaxError` at import time, so `main_ex2.py` will not load at all.
- **`source/scripts/ex_as_fun_2.py:1404`** — `run_wave_washer` calls `sys.exit()` when the dialog is cancelled, but this function does not `import sys` (unlike the slinky/helical/getting-input wrappers in the same file). On cancel it raises `NameError: name 'sys' is not defined` instead of exiting cleanly.
- **`source/scripts/ex_as_fun_2.py:643`** (`run_getting_user_input`) — uses `sys.exit(...)` on out-of-range input but never imports `sys` inside the function (the file-level `from __future__ import division` does not bring in `sys`). Any short-circuit validation path raises `NameError`. Same latent defect exists in `source/main_ex1.py:382/387/392` and `source/main_ex2.py:405/410/415`, which rely on a module-level `import sys` that is present there, so those are fine — but the `ex_as_fun_2.py` copy is broken.

## Medium
- **`source/main_ex1.py:339,356,359` and `source/main_ex2.py:362,379,382` (`run_gear_example`)** — `print(SizeFile, '...%f' % ...)` was mechanically converted from the Python-2 `print SizeFile, '...'`. As written it does NOT write to the file; it prints the tuple `(SizeFile, 'string')` to stdout. The intended file output (gear pitch-diameter lines) is silently lost, while only the `print >> SizeFile` lines (`main_ex1.py:347`) actually reach the file. The data the script is supposed to record is dropped.
- **`source/main_ex1.py:359-360` and `source/main_ex2.py:382-383`** — the `print(... Profile2.PitchDiameter` statement has its closing `)` on the next line by itself, splitting the call across lines mid-token in a way that, combined with the `print(SizeFile, ...)` shape above, makes the intent unrecoverable; the second-gear size line is never written to the file as intended.
- **`source/main_ex2.py:45`** — `exec(open(script_path).read(), globals())` opens the script file without closing it (no `with`). Under IronPython this leaks a file handle per script execution and can keep the script file locked. `source/main.py:57-58` does this correctly with `with open(...)`.
- **`source/main.py:43-45`** — the connection setup uses a bare `except:` that swallows every error (including `KeyboardInterrupt`/`SystemExit`) and reports a generic "Alibre Design not found" regardless of the real cause (e.g., a COM/marshal error or assembly-load failure), masking the actual fault. `source/main_ex3.py:32-33,42-43` has the same bare-`except: pass` pattern, fully swallowing geometry-iteration errors so vertex enumeration failures are invisible.

## Low
- **`source/main.py:111-119`** — `menu_definitions` maps a top-level "Examples" menu to a folder named `"examples"`, but the project ships its examples under `scripts/` and `prototypes/`/`randd/`; there is no `examples` folder. The "Examples" menu will always be empty (skipped by the `os.path.isdir` guard), so the advertised Examples menu never appears.
- **`source/prototypes/Equation-Editor-Function-Calling.py:15`** — `EquationEditorForm.__init__` never calls the base `Form.__init__(self)` before setting properties and adding controls. With IronPython subclassing of WinForms `Form`, skipping the base constructor is fragile and can leave the native control uninitialized; it works only by luck of the CLR wrapper. Should call `super(EquationEditorForm, self).__init__()` (or `Form.__init__(self)`) first.
- **`source/prototypes/Equation-Editor-Function-Calling.py:95,103`** — `eval(new_text, self.EVAL_GLOBALS, param_values)` with `"__builtins__": None`. `OnEquationChanged` wraps this in a bare `except:` and shows "..." on any failure, but `OnSendButtonClicked` will accept any expression that happens to evaluate; e.g. an empty/whitespace equation makes `eval("")` raise (caught) — acceptable — but a parameter named like a Python keyword or containing a leading digit becomes an invalid local-name binding in `param_values` and silently shadows nothing, so such parameters are unusable in equations without warning. Minor robustness gap, not a crash.

## Notes on items checked and deemed NOT bugs
- **Lambda late-binding in menu loops** (`source/main.py:136,154`; `source/main_ex2.py:57`; `source/main_ex1.py:967`/`main_ex2.py:990`) — each correctly captures the loop variable via a default argument (`path=script_path`, `script=example`, `f=func`), so all menu items invoke the right target. Not the classic closure bug.
- **STA thread + `Application.Run` + `t.Join()`** (`source/main.py:179-182`, and the same in `main_ex1/2/3`) — running WinForms on a dedicated STA thread and joining is correct; the apartment state is set before `Start()`.
- **Integer division under IronPython 2.7** — checked the division-sensitive examples. `ex_as_fun_1.py` (raw listings) and `ex_as_fun_2.py` both begin with `from __future__ import division`, so `/` is true division there; the `Tool-Cutting` math in `ex_as_fun_2.py:1260,1270` (`180 / StepAngle`, `TotalAngle / StepAngle`) yields floats but is only used in `range(0, ...)` (IronPython `range` accepts a float-valued result of integer-valued division) and as plane counts — values are integral, so no off-by-one. The `main_ex1.py`/`main_ex2.py` copies use explicit `//` (`180 // StepAngle`, `TotalAngle // StepAngle`) and are correct. `Mobius` uses `Rotations / float(Steps)` explicitly. No latent integer-truncation defects found.
- **`run_wave_washer` P1/P2 indexing** in `source/main_ex1.py:869-871` / `main_ex2.py:892-894` — reads `PathPoints[0..5]`; the `while` loop always appends at least two points before the `t >= t_max` break, so those indices always exist. Not an out-of-range bug. (`ex_as_fun_2.py:1422-1430` captures P1/P2 inside the loop, which is also fine.)
- **`Equation-Editor` `OnEquationChanged` bare `except`** — intentional: it is a live-preview handler where any parse error should just show "..."; swallowing is appropriate here (the send path reports errors via a dialog).
